# AWG Console

Панель управления одним сервером Ubuntu 22.04/24.04 `amd64` с тремя VPN: AmneziaWG и Hysteria2 с
обфускацией плюс MTProto-прокси на движке `telemt` — пользователи, профили, состояние интерфейсов,
Fail2ban и шифрованные бэкапы. Один инстанс = один узел.

## Архитектура

Два изолированных слоя, привилегирован только хост-слой.

| Слой | Где работает | От чего защищён |
| --- | --- | --- |
| `app/` (FastAPI + SQLite) | контейнер под uid `10001`, `cap_drop ALL`, `no-new-privileges`, `read_only`, сокет смонтирован `:ro` | не видит файлы хоста, не может выполнить `awg`/`ip` напрямую |
| `host-agent/agent.py` | служба `awg-panel-agent.service` от root | Unix-сокет `0660` с группой контейнера, жёсткий список операций, никакой passthrough команд |

Веб-слой общается с агентом только JSON-запросами (`status`, `create`, `enable`, `disable`, `delete`,
`proxy`, `fail2ban`, `settings`, `backups`, `hysteria`, `mtproto`, `mt_stats`, `mtproto_create`,
`mtproto_action`, `mtproto_domain`, `mtproto_pool`). Ни одна пользовательская строка не попадает в
shell: команды собираются списками аргументов, а запросы к движку — жёстким списком путей Control API.

Hysteria2 устроена иначе: её пользователи живут только в БД панели, а сервер обращается к панели по
HTTP (`auth.type: http` → `POST /authenticate`). Поэтому создание, отключение и удаление клиента
Hysteria2 не требует ни одной привилегированной операции на хосте — агент отдаёт лишь read-only
снимок конфига (порт, отпечаток сертификата, obfs, состояние службы) для сборки ссылки.

MTProto — третий вариант: клиенты принадлежат не панели, а самому движку. Агент ходит в Control API
`telemt` на loopback и ничего не пишет в файловую систему, а `telemt.toml` меняет сам движок по той
же ссылке. Ни имён, ни секретов MTProto в SQLite панели нет.

## Модель peer'ов

Каждый клиент — отдельный drop-in-файл `PEERS_DIR/<имя>.conf` с блоком `[Peer]`, который агент навешивает
командой `awg addconf <интерфейс> <файл>`.

- Основной `awg0.conf` панель **не переписывает** — риск испортить чужие профили и серверные ключи отсутствует.
- Отключённый peer переименовывается в `<имя>.conf.disabled`: `awg-quick@awg0.service` при загрузке его
  не увидит, то есть «выключен» означает «не поднимется и после перезагрузки».
- `awg-quick` читает только основной конфиг, поэтому drop-in'ы применяет отдельная oneshot-служба
  `awg-panel-peers.service` (`agent.py --apply`, `After=awg-quick@awg0.service`).
- Все правки идут под `flock` (`PEERS_DIR/.lock`), запись атомарная (`temp` + `os.replace`, режим `0600`).
  Если `addconf` упал, файл peer'а удаляется — «сироты» не остаётся.
- Порядок при создании: сначала peer возникает на хосте, потом строка в БД. Если INSERT упал, агент
  получает компенсирующий `delete`. Повтор имени отсекается ещё до обращения к хосту (уникальность в БД +
  проверка имён файлов), на `vpn_user(public_key)` висит уникальный индекс.

Приватный ключ клиента генерируется на хосте, отдаётся ровно один раз (страница профиля, скачивание, QR)
и нигде не сохраняется: в БД и в drop-in'е лежат только публичный ключ и адрес.

## Пользователи Hysteria2

Таблица `hysteria_user` (`name` уникален вместе с `vpn_user`, пароль ссылки, `status`, `expires_at`,
`last_used_at`). Ссылка собирается на лету из параметров узла, которые отдаёт операция `hysteria`:

```
hysteria2://<пароль>@<адрес>:43522/?insecure=1&pinSHA256=<отпечаток>&sni=<домен>&obfs=salamander&obfs-password=<из конфига>
```

`insecure=1` и `pinSHA256` идут в паре: сертификат самоподписанный, цепочку CA проверить нельзя, но
пин по отпечатку обязателен — иначе MITM подменит сервер. Пароль ссылки хранится в БД открытым текстом,
иначе панель не смогла бы отдавать её повторно; файл БД читают только root и uid контейнера, архивы
бэкапов шифруются. Просроченные клиенты выключаются тем же `expire_users`, что и peer'ы AmneziaWG.

## Клиенты MTProto

Раздел `/mtproto` управляет движком `telemt` и только им. Таблицы MTProto в базе панели нет:
единственный источник правды — `GET /v1/users` самого движка, поэтому карточка клиента всегда
ровно то, что вернул Control API, а удаление клиента из движка не может «остаться» в панели.

Последнего клиента удалить нельзя, и это не политика панели, а свойство движка: с пустой
`[access.users]` `telemt` выдаёт `Invalid config: No users configured` и не поднимается после
перезагрузки. Поэтому панель не искушает оператора — пока клиент один, кнопка «Удалить» не
выводится, вместо неё в карточке подсказка, а доступными остаются «Отключить» и «Новый секрет».
Отказы движка (`409 last_user_forbidden`, `409 user_exists`) переводятся на русский с самим кодом
в скобках, потому что голый код оператору ни о чём не говорит. Ключ перевода — пара (действие, код):
тот же `last_user_forbidden` вне удаления ничего не значит, а `not_found` и прочие коды идут общим
шаблоном «Движок не выполнил <действие> клиента <имя>: <код>».

Панель не вызывает бинарь прокси и не правит `telemt.toml`. Все действия идут через хост-агент
(операции `mtproto`, `mt_stats`, `mtproto_create`, `mtproto_action`, `mtproto_domain`,
`mtproto_pool`), а он — через Control API движка на `127.0.0.1:9091` с токеном из
`MTPROTO_API_TOKEN`. Список разрешённых вызовов жёстко зашит в `host-agent/agent.py`:

| Действие панели | Запрос к движку |
| --- | --- |
| список и карточки | `GET /v1/users` |
| создать клиента | `POST /v1/users` (тело только `{"username": …}`) |
| включить / выключить | `POST /v1/users/{name}/enable` / `…/disable` |
| сменить секрет и ссылки | `POST /v1/users/{name}/rotate-secret` |
| удалить | `DELETE /v1/users/{name}` |
| подменный домен и его пул | `GET /v1/config`, `PATCH /v1/config?reload=drain&timeout_secs=30` |
| статус перегрузки генерации | `GET /v1/system/reload/{id}` |
| версия и аптайм | `GET /v1/system/info` |

Секрет клиента (32 hex) генерирует движок, панель его не подбирает и не хранит: он отдаётся один
раз в ответе создания и `rotate-secret`, а ссылка строится там же. ee-ссылка несёт домен внутри
(`secret + hex(домен)`), поэтому переключение `tls_domain` само по себе сделало бы ранее выданные
ссылки нерабочими («Unknown TLS SNI») — при переключении прежний домен остаётся в пуле
`tls_domains`, и панель предлагает этот выбор явно (флажок «держать прежние ссылки»). Ссылка
режима `dd` домена не несёт вовсе.

`enable`/`disable` движок хранит в `[access]` и применяет горячей перезагрузкой, а вот `tls_domain`,
`tls_domains` и `unknown_sni_action` — Hot-Reload ✘: их применит только перезапуск генерации. Панель
просит `reload=drain` с `timeout_secs=30` (30 с живут сессии старой генерации), дожидается статуса
`GET /v1/system/reload/{id}` и никогда не выдаёт «применено», пока статуса нет. На `telemt` 3.5.16
переключение домена проходит `preparing → succeeded` примерно за 11 с, `failure_policy` при этом
`keep_new`; второй PATCH, пока первая перегрузка не закончилась, движок отклоняет
(`reload_in_progress`), и панель показывает именно эту ошибку. Патч, совпадающий с действующим
конфигом, новую генерацию не поднимает вовсе (`runtime_reload_required = false`), и раздел говорит
«в конфиге ничего не изменилось», а не «ещё идёт». Кэш TLS-профилей в `tls_front_dir` движок
наполняет сам по ходу подготовки генерации — прогревать профиль вручную не нужно.

Стартовать без клиентов движок вообще не может: пустая `[access.users]` — не «нуль клиентов», а
отказ конфигурации (`Invalid config: Config error: No users configured`), и пустая строка в качестве
секрета даёт ровно тот же отказ. Поэтому в `host-agent/telemt/telemt.toml` лежит клиент `bootstrap`
с пустым секретом, который заполняется на узле, а настоящий клиент создаётся панелью; после этого
bootstrap удаляется через раздел. Вторая цена незнания этого места: `POST /v1/users` падает с
`failed to write config: Operation not permitted`, если `telemt.toml` принадлежит `root:telemt` —
юнит движка работает без `CAP_CHOWN`, поэтому файл обязан принадлежать самому движку.

## Кто в сети сейчас

Статус `active` в БД означает «разрешено», а не «подключено». Отдельный признак жизни дают сами узловые
счётчики, и для трёх протоколов он разный.

**AmneziaWG.** В ядре нет поля «соединение живо»: есть время последнего рукопожатия, счётчики
принято/отдано и адрес клиента. Рукопожатие обновляется только на rekey, поэтому молчащий, но поднятый
туннель держит старый timestamp — одного порога по времени мало. Панельный профиль идёт с
`PersistentKeepalive = 25`, и живой клиент даже в простое шлёт пакеты, которые двигают счётчик
принятого. Отсюда правило: **онлайн = рукопожатие свежее `HANDSHAKE_TTL` (180 с) ИЛИ прирост
принятых байт в окне `TRAFFIC_WINDOW` (90 с)**. На замере живого клиента (20 проб `awg show awg0 dump`
с шагом 10 с) рукопожатие обновлялось примерно раз в 120 с — максимальный возраст за прогон 113 с, —
а принятые байты двигались в 19 интервалах из 19. Источник — одна команда `awg show <iface> dump`
(операция агента `peers`): в `dump` строка интерфейса начинается с приватного ключа сервера, поэтому
peer опознаётся по форме остальных полей, и ни один ключ, кроме публичного ключа клиента, не уходит с
узла. Голый `awg show <iface>` не используется именно поэтому.

**Hysteria2.** Источник — Traffic Stats API самого сервера (`trafficStats.listen` + `secret` в
`/etc/hysteria/config.yaml`, операция агента `hy2_stats`): `GET /online` отдаёт число активных
QUIC-соединений по имени, которое вернул `/authenticate`, `GET /traffic` — счётчики байт. Карта
соединений живёт в памяти hysteria: после `systemctl restart hysteria-server` она пустеет, живые
клиенты возвращаются в неё сами в пределах keepalive (~30 с). Порт API должен смотреть только на
loopback — `POST /kick` и `GET /dump/streams` умеют рвать чужие соединения.

**MTProto.** Источник — сам движок: операция `mt_stats` (это `GET /v1/users`, но без ссылок, чтобы
секреты не ходили по пути 30-секундного опроса) и поле `current_connections` у каждого клиента.
Правило простое: соединения больше нуля — «В СЕТИ»; нули при `enabled = true` — «НЕТ В СЕТИ»; нули
при выключенном клиенте — «НЕТ В СЕТИ» с пояснением «клиент выключен»; клиента нет в ответе движка —
«НЕ В РАНТАЙМЕ» с текстом «клиента нет в конфиге движка»; API не ответил или `MTPROTO_API_URL` пуст —
«УЗЕЛ НЕ ОТВЕТИЛ» с текстом ошибки. Отдельного окна по трафику здесь нет: движок сам считает активные
соединения, и они не зависят от телеметрии, в отличие от байтов и адресов клиента.

Опрос узла — фоновый цикл панели раз в `POLL_SECONDS` (30 с) плюс обновление страницы, если снимок
старше 20 с: дельта счётчика требует двух замеров, и иначе она была бы видна только тому, кто обновил
страницу дважды. Если источник не ответил (интерфейс пропал, API недоступен, `HYSTERIA_STATS_URL`
пуст), панель не рисует «нет в сети» — она показывает «узел не ответил» и отдельное предупреждение,
потому что сбой опроса и отсутствие клиента — разные вещи.

## Конфигурация

`/etc/awg-panel/agent.conf` (root:root `0600`) — параметры хост-агента. Порядок слияния:
значения по умолчанию → файл → переменные окружения.

| Ключ | По умолчанию | Назначение |
| --- | --- | --- |
| `AWG_BIN` / `IP_BIN` / `FAIL2BAN_BIN` | `/usr/bin/awg`, `/usr/sbin/ip`, `/usr/bin/fail2ban-client` | пути к бинарям |
| `INTERFACE` | `awg0` | имя интерфейса AmneziaWG |
| `NETWORK` | `10.66.0.0/24` | пул адресов клиентов |
| `GATEWAY_ADDRESS` | `10.66.0.1` | адрес интерфейса; исключается из выдачи и обязан входить в `NETWORK` |
| `INTERFACE_CONFIG` | `/etc/amnezia/amneziawg/awg0.conf` | источник `[Interface]`-параметров (в т.ч. junk-отпечатка `Jc/Jmin/Jmax/S1/S2/H1..H4`) для профилей клиента |
| `PEERS_DIR` | `/etc/amnezia/amneziawg/panel-peers` | каталог drop-in'ов (`0700`) |
| `SOCKET_PATH` / `SOCKET_GROUP` | `/run/awg-panel/agent.sock` / `10001` | сокет агента и группа, которой дан доступ (`0660`) |
| `ENDPOINT_DEV` / `PUBLIC_ENDPOINT` | `ens3` / пусто | откуда взять внешний адрес для `Endpoint =` |
| `CLIENT_DNS` | `1.1.1.1` | `DNS =` в выдаваемом профиле |
| `COMMAND_TIMEOUT` | `5` | секунды, диапазон `1–60` |
| `HYSTERIA_CONFIG` / `HYSTERIA_CERT` | `/etc/hysteria/config.yaml` / `/etc/hysteria/tls.crt` | откуда агент читает порт, obfs и отпечаток сертификата для ссылок |
| `HYSTERIA_SERVICE` / `HYSTERIA_SNI` | `hysteria-server` / пусто | имя systemd-юнита и SNI, который кладётся в ссылку |
| `HYSTERIA_STATS_URL` / `HYSTERIA_STATS_SECRET` | пусто / пусто | Traffic Stats API hysteria2 (`http://127.0.0.1:9999` и secret для заголовка `Authorization`); пусто → онлайн по Hysteria2 не определяется |
| `MTPROTO_API_URL` | пусто | Control API движка `telemt` (`http://127.0.0.1:9091`); пусто → весь раздел MTProto отдаёт «не настроен», агент не делает ни одного HTTP-запроса |
| `MTPROTO_API_TOKEN` | пусто | значение заголовка `Authorization` целиком: telemt сверяет строку точно, поэтому здесь нужно писать `Bearer <токен>` и то же самое в `auth_header` конфига движка; пусто → запросы без авторизации |
| `MTPROTO_SERVICE` | `telemt` | имя systemd-юнита движка, нужно только для `is-active` в карточке «ДВИЖОК»; пусто → состояние не показывается |
| `OPENSSL_BIN` / `SYSTEMCTL_BIN` | `/usr/bin/openssl` / `/usr/bin/systemctl` | нужны только для `-fingerprint -sha256` и `is-active` |
| `BACKUP_SOURCE_DB` | `/opt/awg-panel/data/panel.sqlite3` | БД панели |
| `BACKUP_DIR` / `BACKUP_KEY_FILE` / `BACKUP_RETENTION` | `/var/backups/awg-panel` / `/etc/awg-panel/backup.key` / `7` | куда писать, чем шифровать, сколько архивов хранить |

`.env` рядом с `docker-compose.yml` — только веб-слой: `PANEL_PORT`, `PANEL_BIND` (по умолчанию
`127.0.0.1`), `ADMIN_LOGIN`, `SESSION_SECRET` (≥ 32 символов), `ADMIN_PASSWORD` (нужен лишь на первом
старте), `AGENT_SOCKET`, `AGENT_TIMEOUT`, `AUDIT_LOG` (пусто → аудит пишется только в лог контейнера).

Каталог сокета в `/run` создаёт не агент, а systemd: `/run` — tmpfs, который обнуляется при каждой
загрузке, а юнит агента идёт с `ProtectSystem=strict` и `ReadWritePaths=/run/awg-panel`, где
bind-монтирование отсутствующего пути обрывает старт ещё до Python (`226/NAMESPACE`). Поэтому в
`install.sh` ставится `host-agent/awg-panel.tmpfiles` → `/etc/tmpfiles.d/awg-panel.conf`, а
`systemd-tmpfiles-setup` гарантированно раньше `multi-user.target`. Тот же механизм требует, чтобы
`/var/backups/awg-panel` создавал установщик (см. «Бэкапы»).

## Разделы и маршруты

Шесть разделов с общей навигацией слева и возвратом «← На главную» во вторичных страницах:

| Раздел | Маршрут | Что показывает |
| --- | --- | --- |
| Обзор | `/` | AmneziaWG, интерфейс и UDP-порт, peer'ы в рантайме и в панели, «В СЕТИ СЕЙЧАС» по всем трём протоколам, MTProto, Fail2ban |
| Пользователи | `/users` | оба протокола: AmneziaWG-профили и ссылки Hysteria2, создание, включить/выключить/удалить, смена пароля ссылки, срок доступа; у каждой карточки — бейдж «в сети / нет в сети / не было рукопожатия» с адресом клиента, возрастом рукопожатия и байтами |
| MTProto | `/mtproto` | состояние движка (версия, юнит, аптайм), клиенты из `GET /v1/users` с бейджем «в сети» по `current_connections`, ee-ссылки по каждому домену пула и `dd`-ссылки, QR; создание, включить/выключить, ротация секрета, удаление (кнопки нет, пока клиент в движке один); смена подменного домена и пула прежних доменов |
| Службы узла | `/services` | версия и рантайм AWG, юнит и клиенты `telemt`, счётчики каждого jail'а Fail2ban; список забаненных адресов свёрнут в «Показать (N)», разворачивается по клику, там же кнопки «Разбанить» и форма ручного бана |
| Бэкапы | `/backups` | архивы из `BACKUP_DIR`, наличие БД и ключа шифрования, лимит хранения |
| Настройки | `/settings` | действующие значения `agent.conf` глазами агента и смена пароля администратора |

Профиль клиента и QR — `/users/config`, выдача файла — `/users/config/download`; Hysteria2 —
`POST /hysteria`, `POST /hysteria/{id}/{enable|disable|delete|rotate}`, QR — `/hysteria/{id}/qr`;
MTProto — `POST /mtproto` (создание), `POST /mtproto/{name}/{enable|disable|delete|rotate}`,
смена домена — `POST /mtproto/domain` с флагом `keep_previous`, пул прежних доменов —
`POST /mtproto/pool`, QR — `/mtproto/{name}/qr?domain=<из пула>`; ручной бан — `POST /fail2ban`
с полями `action=ban|unban`, `jail`, `ip`; служебное — `/healthz`, `/login`, `/logout`.
`/authenticate` вызывает сам сервер Hysteria2: он сверяет пароль с БД, отмечает `last_used_at`
и пишет исходный адрес клиента в аудит.

Разделы только читают состояние, кроме явных действий над peer, ссылкой Hysteria2, клиентом и
конфигом MTProto, сменой пароля и одного адреса в Fail2ban.

Защита входа: scrypt-хеш пароля, подписанная cookie-сессия (`HttpOnly`, `SameSite=Strict`, 8 часов),
CSRF-токен в сессии на всех POST, лимитер `5` неудачных попыток на `15` минут по IP. Просроченные
пользователи отключаются и на хосте (`expire_users` при заходе + фоновый цикл раз в минуту).

Подпись в шапке описывает хост-агент, а не наличие WireGuard-интерфейса: `ХОСТ: awg0` там, где раздел
спрашивал интерфейс, `ХОСТ: агент отвечает` в `/mtproto` и `/backups` (агент ответил, интерфейса там
нет), `ХОСТ: агент не ответил` при сентинеле `host-side adapter …` из `app/awg.py` и «хост-агент здесь
не опрашивался» на `/users/config`. Прежняя формулировка «БЕЗ ХОСТ-АГЕНТА» показывала отсутствие агента
прямо над живым списком клиентов — это была правда только для WG-страниц.

## Установка

```bash
sudo ./install.sh                                   # панель на 127.0.0.1, доступ через SSH-туннель
sudo ./install.sh --with-fail2ban                   # + jails для sshd, входа в панель и Hysteria2
sudo ./install.sh --expose-firewall                 # привязка 0.0.0.0 и правило ufw
PANEL_PORT=44090 ADMIN_LOGIN=admin sudo -E ./install.sh --expose-firewall
```

Скрипт ставит Docker, если его нет, копирует код в `/opt/awg-panel`, создаёт `agent.conf` из примера,
готовит `/var/log/awg-panel/audit.log` и `/etc/awg-panel/backup.key`, включает `awg-panel-agent`,
`awg-panel-peers`, `awg-panel-backup.timer`, собирает контейнер, ждёт `/healthz` и удаляет
`ADMIN_PASSWORD` из `.env`. Порт по умолчанию берётся из `PANEL_PORT`, иначе — первый свободный из
`5000`, затем `5500–5999`. `ADMIN_PASSWORD` тоже можно передать окружением, тогда он не попадёт ни в
вывод, ни в лог установки; сгенерированный самим скриптом пароль печатается в вывод одной строкой (в
лог — только предупреждение, что первый вход потребует его заменить).

Доступ к панели — HTTP: либо туннель, либо адрес узла напрямую, если она развёрнута с
`--expose-firewall`.

```bash
ssh -L 5000:127.0.0.1:5000 root@server   # затем http://127.0.0.1:5000
```

### Весь узел с нуля: `bootstrap.sh`

`install.sh` — это только панель: Docker, код в `/opt/awg-panel`, хост-агент, юниты, ключ бэкапов и
jail'ы. Интерфейс AmneziaWG, сервер Hysteria2 и движок `telemt` он не касается — на голой Ubuntu их
просто не будет, и панель поднимется без единого прокси.

Для переустановки сервера целиком есть `bootstrap.sh`: шесть этапов в одном порядке
(`base → awg → panel → hysteria → telemt → fail2ban`), после каждого — проверка фактического состояния,
а не кода возврата пакета. Версии чужого бинарника закреплены sha256, а ключ PPA Amnezia — отпечатком:
не совпало — скрипт останавливается и не запускает непроверенный код от root.

```bash
git clone https://github.com/dimmaust/awg_hestera_webpanel.git /root/awg-panel-src
cd /root/awg-panel-src
OPERATOR_IPS=<адрес вашей машины: curl -4 https://ifconfig.co> sudo -E ./bootstrap.sh
sudo ./bootstrap.sh --check                         # только чтение: отчёт по узлу
sudo ./bootstrap.sh --stage telemt                  # один этап после сбоя
sudo ./bootstrap.sh --skip hysteria --force-config  # пропустить этап, пересоздать конфиги
```

`OPERATOR_IPS` — адрес, с которого вы входите по SSH и в панель: он попадает в `ignoreip` jail'а
`sshd` и панели. Без него этап `fail2ban` отказывается ставить jails, потому что `maxretry = 2`
закрыл бы доступ самому оператору.

Придумывать учётки до запуска не нужно: логин веб-консоли задаётся `ADMIN_LOGIN` (по умолчанию
`admin`), пароль скрипт генерирует сам при первом запуске. Он кладётся в файл и печатается в вывод
этого запуска двумя строками — сам пароль и напоминание, что первый вход потребует его заменить; в
`/var/log/awg-panel-bootstrap.log` секрет не пишется. Если файл уже был создан раньше (прерванный и
повторённый прогон), наружу уходит только строка с путём к нему, а пароль по-прежнему лежит здесь:

```bash
sudo cat /root/awg-panel-secrets/admin-password.txt     # пароль от http://<адрес узла>:44090/login
```

Первый вход в панель сразу приводит на страницу смены пароля: пока строка `must_change` в таблице
`administrator` равна 1, ни один раздел не открывается (ни `/users`, ни создание клиента), доступна
только форма. Смена снимает флаг, сбрасывает сессию и требует войти новым паролем; дальше менять его
можно формой в разделе «Настройки» (`POST /settings`) или тем же `/password`. Узел, развёрнутый до
этой правки, замены не требует: `ALTER TABLE` проставляет существующему администратору `must_change = 0`,
потому что его пароль выбирал не установщик.

Другой подготовки, кроме root-доступа к узлу, не требуется: `git clone` берёт и сам скрипт, и код панели,
и шаблоны конфигов, а пакеты, Docker, репозиторий Amnezia и права на каталоги этапы ставят сами.

Скрипт никогда не перезагружает узел, не включает ufw, не правит `sshd_config`, не удаляет чужие конфиги
(старые — в `.bak-<дата>`) и не оставляет секреты в логе: пароль администратора кладётся в
`/root/awg-panel-secrets/admin-password.txt` (0600) и показывается только в терминал запуска, ключи AWG,
obfs-пароль и токены живут только в узловых конфигах и наружу не печатаются вовсе. Порядок шагов и
чек-лист приёма — `docs/install.md`.

## Бэкапы и восстановление

`awg-panel-backup.timer` ежедневно в 03:30 (+ до 5 минут разброса, `Persistent=true`).
`host-agent/backup.py`: снапшот БД через online backup API с `PRAGMA integrity_check`, плюс `awg0.conf`,
`agent.conf` и весь `PEERS_DIR`; tar → `openssl enc -aes-256-cbc -pbkdf2 -iter 200000 -salt` с ключом из
`BACKUP_KEY_FILE`; запись через `.part` + `os.replace` (`0600`); обязательная проверка расшифровкой;
лишние архивы удаляются по `BACKUP_RETENTION`.

**В архиве лежит приватный ключ сервера** (в `awg0.conf`), поэтому он бесполезен без
`/etc/awg-panel/backup.key` — ключ нужно скопировать с узла сразу после установки.

```bash
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 \
  -in /var/backups/awg-panel/awg-panel-<_stamp>.tar.gz.enc \
  -pass file:/etc/awg-panel/backup.key | tar -xzf - -C /restore/awg-panel
```

Юнит сервиса идёт с `ProtectSystem=strict`, то есть корень для него read-only и `mkdir` внутри
`backup.py` не сработает: `/var/backups/awg-panel` обязан создать `install.sh`.

Файл БД контейнер создаёт с дефолтной маской, а в нём пароли клиентов Hysteria2 открытым текстом.
Каталог `data` и так `0700` от uid контейнера, поэтому права на сам файл доводит его создатель —
`app/db.py` ставит `0600` сразу после появления файла: читать его должны только root и uid панели.

## Fail2ban

Политика по умолчанию: **бан на второй неудачной попытке, 30 минут**, а `[recidive]` при повторном
бане в пределах суток закрывает доступ навсегда. Лестница: две неверные попытки за час → бан на 30
минут, второй бан за сутки → DROP навсегда. Одна опечатка в пароле доступ не режет.

Четыре jail'а (`host-agent/fail2ban/jail.d/awg-panel.conf` + `filter.d/awg-panel.conf`,
`filter.d/awg-hy2.conf`, `action.d/awg-panel-docker.conf`):

| Jail | Источник сигнала | Где банит |
| --- | --- | --- |
| `sshd` | `/var/log/auth.log` | `INPUT`, tcp/22 |
| `awg-panel` | `FAILED_LOGIN` из `/var/log/awg-panel/audit.log` | `DOCKER-USER`, все порты контейнера |
| `awg-hy2` | `HY2_AUTH_FAIL` из того же файла | `INPUT`, udp/43522 (`DROP`, чтобы выглядело обрывом сети) |
| `recidive` | `/var/log/fail2ban.log` | `INPUT` + `DOCKER-USER`, навсегда |

Публикация порта Docker — главная ловушка: пакет на `IP:44090` идёт
`PREROUTING(DNAT) -> FORWARD`, поэтому правила в `INPUT` его не касаются. Для панели написан
`awg-panel-docker`, который вставляет прыжок в `DOCKER-USER` — единственную цепочку, куда Docker сам
разрешает вставлять свои фильтры. Тот же переход должен выдерживать перезагрузку: Fail2ban стартует
раньше `dockerd`, и в этой гонке и `actionstart`, и последующие `actionban` не находят `DOCKER-USER`.
Поэтому переход проверяется и доставляется в `actioncheck`, который Fail2ban 0.11.2 вызывает перед
каждым баном, — иначе jail тихо остаётся с цепочкой, в которую никто не заходит.

Свои адреса заносятся в `/etc/fail2ban/jail.d/awg-panel.local` через ключ `operator_ip` — файл
`.local` имеет приоритет над `awg-panel.conf` и `install.sh` его не перезаписывает. Базовый
`ignoreip` (`127.0.0.0/8`, docker-подсеть `172.18.0.0/16`, пул AWG `10.66.0.0/24`) уже в конфиге
панели: адрес docker-шлюза там не зря — запросы самого узла к панели приходят именно с него, и его
бан отключил бы авторизацию Hysteria2 на всём узле.

Агент читает состояние (`fail2ban-client status <jail>`), а пишет ровно один раз — ручной
`ban`/`unban` одного адреса из `/services`, то есть `fail2ban-client set <jail> banip|unbanip <ip>`.
Имя jail'а сверяется со списком, который вернул сам fail2ban, адрес проходит через
`ipaddress.ip_address`, поэтому в argv не уходит ни маска `/32`, ни неизвестный jail, ни пробелы;
обхода `bantime` нет — ручной бан живёт ровно столько, сколько настроено в этом jail'е. Остановку
jail'а, `reload` сервиса и правку `maxretry` панель сознательно не предоставляет: это остаётся за
SSH. Каждое действие пишется в аудит (`F2B_BAN`, `F2B_UNBAN`), и эти строки сами себе бан не
выписывают — фильтры заякорены на `FAILED_LOGIN` и `HY2_AUTH_FAIL`. Jail'ы создаёт
`install.sh --with-fail2ban`. Ubuntu 22.04 ставит `banaction = iptables-multiport`, а `iptables` там —
обёртка над `nf_tables` (`iptables v1.8.7 (nf_tables)`), поэтому баны видны и в `iptables -S`, и в
`nft list ruleset`.

### `/authenticate` принимает адрес клиента только от локального источника

Hysteria2 зовёт панель со самого узла и кладёт адрес клиента в поле `addr` тела запроса.
Панель опубликована в интернет по тому же порту, поэтому наивная обработка превращала `addr`
в переключатель цели бана: любой, кто знает порт, выписал бы бан любому адресу чужими руками
— а два таких события `recidive` закрывает навсегда и по всем портам. Теперь `/authenticate`
сначала смотрит на настоящий адрес соединения: вне loopback и docker-подсети (`127.0.0.0/8`,
`::1`, `172.16.0.0/12` — с моста приходят и собственные запросы узла к своему опубликованному
порту) запрос отвергается `403`, а в аудит идёт источник, а не подставленный `addr`.

## Что здесь не проверено

- Что молчащий, но поднятый туннель AmneziaWG остаётся «в сети» — это вывод из механики
  (`PersistentKeepalive = 25` + окно по трафику), а не замер на конкретном узле. Если такой туннель
  однажды прочитается как «НЕТ В СЕТИ», правится одним числом — `HANDSHAKE_TTL` в `app/presence.py`.
- Как быстро гаснет бейдж «В СЕТИ» после того, как туннель реально закрылся: порога «закрылось →
  нет соединений» никто не измерял.
- Внешний вид на узких экранах и поведение живого UI после деплоя — глазами оператора;
  автоматизированная проверка только структурная.
