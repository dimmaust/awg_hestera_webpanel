# Архитектура: слои, peer'ы, клиенты, «кто в сети»

Про порядок установки и приёмку узла — [`install.md`](install.md), про переменные конфига —
[`config.md`](config.md), про разделы и маршруты веб-интерфейса — [`interface.md`](interface.md).

## Два изолированных слоя, привилегирован только хост-слой

| Слой | Где работает | От чего защищён |
| --- | --- | --- |
| `app/` (FastAPI + SQLite) | контейнер под uid `10001`, `cap_drop ALL`, `no-new-privileges`, `read_only`, сокет смонтирован `:ro` | не видит файлы хоста, не может выполнить `awg`/`ip` напрямую |
| `host-agent/agent.py` | служба `awg-panel-agent.service` от root | Unix-сокет `0660` с группой контейнера, жёсткий список операций, никакой passthrough команд |

Веб-слой общается с агентом только JSON-запросами (`status`, `create`, `enable`, `disable`, `delete`,
`proxy`, `fail2ban`, `settings`, `backups`, `hysteria`, `mtproto`, `mt_stats`, `mtproto_create`,
`mtproto_action`, `mtproto_domain`, `mtproto_pool`). Ни одна пользовательская строка не попадает в
shell: команды собираются списками аргументов, а запросы к движку — жёстким списком путей Control API.

Hysteria2 устроена иначе: её пользователи живут только в БД панели, а сервер обращается к панели по
HTTP (`auth.type: http` → `POST /authenticate`). Поэтому создание, отключение и удаление клиента
Hysteria2 не требует ни одной привилегированной операции на хосте — агент отдаёт лишь read-only
снимок конфига (порт, отпечаток сертификата, obfs, состояние службы) для сборки ссылки.

MTProto — третий вариант: клиенты принадлежат не панели, а самому движку. Агент ходит в Control API
`telemt` на loopback и ничего не пишет в файловую систему, а `telemt.toml` меняет сам движок по той
же ссылке. Ни имён, ни секретов MTProto в SQLite панели нет.

## Модель peer'ов AmneziaWG

Каждый клиент — отдельный drop-in-файл `PEERS_DIR/<имя>.conf` с блоком `[Peer]`, который агент навешивает
командой `awg addconf <интерфейс> <файл>`.

- Основной `awg0.conf` панель **не переписывает** — риск испортить чужие профили и серверные ключи отсутствует.
- Отключённый peer переименовывается в `<имя>.conf.disabled`: `awg-quick@awg0.service` при загрузке его
  не увидит, то есть «выключен» означает «не поднимется и после перезагрузки».
- `awg-quick` читает только основной конфиг, поэтому drop-in'ы применяет отдельная oneshot-служба
  `awg-panel-peers.service` (`agent.py --apply`, `After=awg-quick@awg0.service`).
- Все правки идут под `flock` (`PEERS_DIR/.lock`), запись атомарная (`temp` + `os.replace`, режим `0600`).
  Если `addconf` упал, файл peer'а удаляется — «сироты» не остаётся.
- Порядок при создании: сначала peer возникает на хосте, потом строка в БД. Если INSERT упал, агент
  получает компенсирующий `delete`. Повтор имени отсекается ещё до обращения к хосту (уникальность в БД +
  проверка имён файлов), на `vpn_user(public_key)` висит уникальный индекс.

Приватный ключ клиента генерируется на хосте, отдаётся ровно один раз (страница профиля, скачивание, QR)
и нигде не сохраняется: в БД и в drop-in'е лежат только публичный ключ и адрес.

## Пользователи Hysteria2

Таблица `hysteria_user` (`name` уникален вместе с `vpn_user`, пароль ссылки, `status`, `expires_at`,
`last_used_at`). Ссылка собирается на лету из параметров узла, которые отдаёт операция `hysteria`:

```
hysteria2://<пароль>@<адрес>:43522/?insecure=1&pinSHA256=<отпечаток>&sni=<домен>&obfs=salamander&obfs-password=<из конфига>
```

`insecure=1` и `pinSHA256` идут в паре: сертификат самоподписанный, цепочку CA проверить нельзя, но
пин по отпечатку обязателен — иначе MITM подменит сервер. Пароль ссылки хранится в БД открытым текстом,
иначе панель не смогла бы отдавать её повторно; файл БД читают только root и uid контейнера, архивы
бэкапов шифруются. Просроченные клиенты выключаются тем же `expire_users`, что и peer'ы AmneziaWG.

## Клиенты MTProto

Раздел `/mtproto` управляет движком `telemt` и только им. Таблицы MTProto в базе панели нет:
единственный источник правды — `GET /v1/users` самого движка, поэтому карточка клиента всегда
ровно то, что вернул Control API, а удаление клиента из движка не может «остаться» в панели.

Последнего клиента удалить нельзя, и это не политика панели, а свойство движка: с пустой
`[access.users]` `telemt` выдаёт `Invalid config: No users configured` и не поднимается после
перезагрузки. Поэтому панель не искушает оператора — пока клиент один, кнопка «Удалить» не
выводится, вместо неё в карточке подсказка, а доступными остаются «Отключить» и «Новый секрет».
Отказы движка (`409 last_user_forbidden`, `409 user_exists`) переводятся на русский с самим кодом
в скобках, потому что голый код оператору ни о чём не говорит. Ключ перевода — пара (действие, код):
тот же `last_user_forbidden` вне удаления ничего не значит, а `not_found` и прочие коды идут общим
шаблоном «Движок не выполнил <действие> клиента <имя>: <код>».

Панель не вызывает бинарь прокси и не правит `telemt.toml`. Все действия идут через хост-агент
(операции `mtproto`, `mt_stats`, `mtproto_create`, `mtproto_action`, `mtproto_domain`,
`mtproto_pool`), а он — через Control API движка на `127.0.0.1:9091` с токеном из
`MTPROTO_API_TOKEN`. Список разрешённых вызовов жёстко зашит в `host-agent/agent.py`:

| Действие панели | Запрос к движку |
| --- | --- |
| список и карточки | `GET /v1/users` |
| создать клиента | `POST /v1/users` (тело только `{"username": …}`) |
| включить / выключить | `POST /v1/users/{name}/enable` / `…/disable` |
| сменить секрет и ссылки | `POST /v1/users/{name}/rotate-secret` |
| удалить | `DELETE /v1/users/{name}` |
| подменный домен и его пул | `GET /v1/config`, `PATCH /v1/config?reload=drain&timeout_secs=30` |
| статус перегрузки генерации | `GET /v1/system/reload/{id}` |
| версия и аптайм | `GET /v1/system/info` |

Секрет клиента (32 hex) генерирует движок, панель его не подбирает и не хранит: он отдаётся один
раз в ответе создания и `rotate-secret`, а ссылка строится там же. ee-ссылка несёт домен внутри
(`secret + hex(домен)`), поэтому переключение `tls_domain` само по себе сделало бы ранее выданные
ссылки нерабочими («Unknown TLS SNI») — при переключении прежний домен остаётся в пуле
`tls_domains`, и панель предлагает этот выбор явно (флажок «держать прежние ссылки»). Ссылка
режима `dd` домена не несёт вовсе.

`enable`/`disable` движок хранит в `[access]` и применяет горячей перезагрузкой, а вот `tls_domain`,
`tls_domains` и `unknown_sni_action` — Hot-Reload ✘: их применит только перезапуск генерации. Панель
просит `reload=drain` с `timeout_secs=30` (30 с живут сессии старой генерации), дожидается статуса
`GET /v1/system/reload/{id}` и никогда не выдаёт «применено», пока статуса нет. На `telemt` 3.5.16
переключение домена проходит `preparing → succeeded` примерно за 11 с, `failure_policy` при этом
`keep_new`; второй PATCH, пока первая перегрузка не закончилась, движок отклоняет
(`reload_in_progress`), и панель показывает именно эту ошибку. Патч, совпадающий с действующим
конфигом, новую генерацию не поднимает вовсе (`runtime_reload_required = false`), и раздел говорит
«в конфиге ничего не изменилось», а не «ещё идёт». Кэш TLS-профилей в `tls_front_dir` движок
наполняет сам по ходу подготовки генерации — прогревать профиль вручную не нужно.

Стартовать без клиентов движок вообще не может: пустая `[access.users]` — не «нуль клиентов», а
отказ конфигурации (`Invalid config: Config error: No users configured`), и пустая строка в качестве
секрета даёт ровно тот же отказ. Поэтому в `host-agent/telemt/telemt.toml` лежит клиент `bootstrap`
с пустым секретом, который заполняется на узле, а настоящий клиент создаётся панелью; после этого
bootstrap удаляется через раздел. Вторая цена незнания этого места: `POST /v1/users` падает с
`failed to write config: Operation not permitted`, если `telemt.toml` принадлежит `root:telemt` —
юнит движка работает без `CAP_CHOWN`, поэтому файл обязан принадлежать самому движку.

## Кто в сети сейчас

Статус `active` в БД означает «разрешено», а не «подключено». Отдельный признак жизни дают сами узловые
счётчики, и для трёх протоколов он разный.

**AmneziaWG.** В ядре нет поля «соединение живо»: есть время последнего рукопожатия, счётчики
принято/отдано и адрес клиента. Рукопожатие обновляется только на rekey, поэтому молчащий, но поднятый
туннель держит старый timestamp — одного порога по времени мало. Панельный профиль идёт с
`PersistentKeepalive = 25`, и живой клиент даже в простое шлёт пакеты, которые двигают счётчик
принятого. Отсюда правило: **онлайн = рукопожатие свежее `HANDSHAKE_TTL` (180 с) ИЛИ прирост
принятых байт в окне `TRAFFIC_WINDOW` (90 с)**. На замере живого клиента (20 проб `awg show awg0 dump`
с шагом 10 с) рукопожатие обновлялось примерно раз в 120 с — максимальный возраст за прогон 113 с, —
а принятые байты двигались в 19 интервалах из 19. Источник — одна команда `awg show <iface> dump`
(операция агента `peers`): в `dump` строка интерфейса начинается с приватного ключа сервера, поэтому
peer опознаётся по форме остальных полей, и ни один ключ, кроме публичного ключа клиента, не уходит с
узла. Голый `awg show <iface>` не используется именно поэтому.

**Hysteria2.** Источник — Traffic Stats API самого сервера (`trafficStats.listen` + `secret` в
`/etc/hysteria/config.yaml`, операция агента `hy2_stats`): `GET /online` отдаёт число активных
QUIC-соединений по имени, которое вернул `/authenticate`, `GET /traffic` — счётчики байт. Карта
соединений живёт в памяти hysteria: после `systemctl restart hysteria-server` она пустеет, живые
клиенты возвращаются в неё сами в пределах keepalive (~30 с). Порт API должен смотреть только на
loopback — `POST /kick` и `GET /dump/streams` умеют рвать чужие соединения.

**MTProto.** Источник — сам движок: операция `mt_stats` (это `GET /v1/users`, но без ссылок, чтобы
секреты не ходили по пути 30-секундного опроса) и поле `current_connections` у каждого клиента.
Правило простое: соединения больше нуля — «В СЕТИ»; нули при `enabled = true` — «НЕТ В СЕТИ»; нули
при выключенном клиенте — «НЕТ В СЕТИ» с пояснением «клиент выключен»; клиента нет в ответе движка —
«НЕ В РАНТАЙМЕ» с текстом «клиента нет в конфиге движка»; API не ответил или `MTPROTO_API_URL` пуст —
«УЗЕЛ НЕ ОТВЕТИЛ» с текстом ошибки. Отдельного окна по трафику здесь нет: движок сам считает активные
соединения, и они не зависят от телеметрии, в отличие от байтов и адресов клиента.

Опрос узла — фоновый цикл панели раз в `POLL_SECONDS` (30 с) плюс обновление страницы, если снимок
старше 20 с: дельта счётчика требует двух замеров, и иначе она была бы видна только тому, кто обновил
страницу дважды. Если источник не ответил (интерфейс пропал, API недоступен, `HYSTERIA_STATS_URL`
пуст), панель не рисует «нет в сети» — она показывает «узел не ответил» и отдельное предупреждение,
потому что сбой опроса и отсутствие клиента — разные вещи.
